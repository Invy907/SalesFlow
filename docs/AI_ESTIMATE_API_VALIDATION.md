# AI 견적 API·앱 검증 실행 가이드

이 가이드는 합성 단가표·과거 견적·설계·작업 상세로 **API 키만 필요한 자동 검증**과 **Supabase가 필요한 실제 앱 검증**을 구분한다. 실제 Gemini·Claude API의 성공 여부는 실행 후 생성된 보고서로 판단한다. 이 문서 자체는 실제 API 호출 성공 기록이 아니다.

## 1. 먼저 실행할 명령

프로젝트 루트에서 실행한다. **Node.js 22를 권장**하며 프로젝트 의존성이 필요하다. 새 체크아웃은 먼저 `npm ci`를 실행한다.

```bash
# 키·DB 없이 합성 자료와 결정적 가격 처리 검증
npm run ai-estimate:validate

# 지원 시나리오와 옵션 확인
npm run ai-estimate:validate -- --list
```

외부 연결을 확인하려면 [환경변수 예제](../scripts/ai-estimate/validation.env.example)를 `.env.ai-validation.local`로 복사하고 사용할 공급자의 키를 입력한다. 이미 같은 파일이 있다면 덮어쓰지 않고 수정한다.

```bash
cp scripts/ai-estimate/validation.env.example .env.ai-validation.local
```

- Gemini: `GEMINI_API_KEY`
- Claude: `ANTHROPIC_API_KEY`
- 모델을 바꿀 때만 예제의 모델 설정을 변경한다. 실제 실행 모델은 보고서에서 확인한다.
- 키는 서버/CLI 전용이다. `NEXT_PUBLIC_` 변수, 브라우저, CSV·본문·프롬프트에 넣지 않는다. 환경 파일을 Git에 커밋하지 않는다.

```bash
# 권장 첫 실제 연결 검사: 원본 PDF 추출 → 그 결과로 견적 생성
npm run ai-estimate:validate -- --live --provider gemini
npm run ai-estimate:validate -- --live --provider anthropic

# 두 공급자를 모두 검사: 두 키가 모두 필요
npm run ai-estimate:validate -- --live --provider all --suite smoke

# 언어·세금·충돌·근거 부족·자료 내 악성 지시까지 확장
npm run ai-estimate:validate -- --live --provider gemini --suite full

# 특정 실패만 재검사
npm run ai-estimate:validate -- --live --provider anthropic --case rate-ko
npm run ai-estimate:validate -- --live --provider gemini --case pdf-to-estimate

# 별도 환경 파일 사용
npm run ai-estimate:validate -- --live --provider gemini --env-file .env.ai-validation.local
```

**API 키가 이미 설정되어 있어도 `--live`를 명시하지 않으면 외부 API를 호출하지 않는다.** 기본 환경 파일은 `.env.ai-validation.local`, 기본 suite는 `smoke`다. **기존 셸 환경변수가 환경 파일보다 우선**하므로 다른 키·모델로 검사할 때는 같은 이름의 셸 변수가 남아 있지 않은지 확인한다. 기본 환경 파일은 없어도 offline 검사를 실행할 수 있지만, `--env-file`로 지정한 파일을 읽지 못하면 설정 오류다. `--provider`를 생략하면 설정된 유효한 키로 자동 선택하며 두 키가 있으면 Gemini를 우선한다. 두 공급자 검증을 의도했다면 반드시 `--provider all`을 지정한다. `--case`는 전체 목록의 단일 ID를 지정할 수 있으며, `pdf-to-estimate`는 선행 `pdf-extraction`을 자동 포함한다.

### 호출량과 판정

| 실행 | 공급자당 모델 작업 | 외부 전송 |
| --- | --- | --- |
| 기본 offline | 0 | 없음 |
| live smoke | PDF 추출 1회 + 연계 생성 1회 = 2회 | 합성 PDF, 승인 자료 역할의 합성 내용·작업 조건 |
| live full | PDF 추출 1회 + 생성 8회 = 9회 | 위 자료와 언어·세금·충돌·근거 부족·주입 시험 입력 |
| live all + smoke / full | 두 공급자 합계 4회 / 18회 | 선택한 각 공급자에 전송 |

위 숫자는 모델 작업 수다. Gemini의 파일 업로드·상태 조회·정리 요청 등 부수 HTTP 요청은 별도이며, 실패나 선행 단계 중단에 따라 실제 수행 작업 수는 줄어들 수 있다. 실제 호출에는 공급자의 사용량·과금 정책이 적용된다. 실행기는 **실패한 모델 작업을 자동 재시도하지 않는다**. 초기 확인은 `smoke`, 실패 원인 수정 후에는 `--case`로 필요한 검사만 직접 실행한다. 파일 처리 상태를 기다리는 조회는 모델 작업 재시도와 다르다.

| 결과 | 해석 |
| --- | --- |
| `PASS` | 해당 검사의 요구 조건을 충족 |
| `SKIPPED_NOT_RUN` | 실제 공급자 호출을 실행하지 않음. API 성공으로 집계하지 않음 |
| `FAIL` | 검사 조건을 충족하지 못함. case·검사 항목·오류 코드 확인 |
| `BLOCKED` | 사전 검사 또는 PDF 선행 추출이 실패해 실행할 수 없음. 성공으로 집계하지 않음 |
| `OFFLINE_PASS_LIVE_NOT_RUN` | 보고서 전체 상태: offline 성공, live 미실행. 개별 live case는 `SKIPPED_NOT_RUN` |
| 종료 코드 `0` | offline 검사 통과 또는 요청한 live 검사 모두 통과 |
| 종료 코드 `1` | 검증 실패 또는 선행 검사 실패 |
| 종료 코드 `2` | 옵션·API 키 등 실행 설정 오류 |

실행 보고서는 `artifacts/ai-estimate-validation/<run>/report.json`과 `report.md`에 저장된다. `--list`·`--help`는 목록/도움말만 출력하며, 실행 전 옵션·키 설정 오류로 종료한 경우 보고서가 생성되지 않을 수 있다. 선택 공급자, 실제 모델, 생성 방식, 검사 항목과 마스킹된 오류를 확인한다. 앱은 외부 생성 실패 시 내부 후보를 정상 반환할 수 있으므로 **live 생성 검사는 `generationMode=model`과 실제 공급자 일치까지 충족해야 한다**. `local` 결과가 화면에 보인다는 사실만으로 API 연결 성공으로 판단하지 않는다.

### JSON에서 사람이 검토할 위치

`cases[]`에서 공급자와 case ID를 찾고 다음 항목을 대조한다. 단계가 중단된 `FAIL`·`BLOCKED` case에는 `output`이 없을 수 있으므로 `error`와 `checks`부터 확인한다.

| JSON 경로 | 확인할 내용 |
| --- | --- |
| `cases[].output.input` | 실제 생성에 보낸 작업 조건·언어·승인 자료 표현 |
| `cases[].output.selectedSourceSnapshots` | 그 요청에 선택한 합성 원본 근거. 예상 파일을 실제 사용했는지 |
| `cases[].output.rawGenerated` | 모델 원안의 수량·수량 이유·단가·경고. 외부 모델 응답이 없으면 `null` |
| `cases[].output.result.draft` | 서버에서 근거와 대조한 최종 초안. 원안과 단가·출처·제외 항목을 비교 |
| `cases[].output.expected` | 해당 시나리오의 기대 품목·단위·수량·가격 근거 |
| `cases[].diagnostics` | 실제 공급자·모델·생성 방식, 생성 HTTP 상태·시도 횟수 또는 추출 지연/토큰 |
| `cases[].output.extracted` / `review` | PDF 추출 원본값과 검수 데이터 변환 결과 (`pdf-extraction`) |
| `cases[].checks` / `error` | 각 assertion의 기대/실제 값 및 안전하게 분류한 오류 |

자동 언어 검사는 해당 언어 문자의 존재 등을 확인하는 제한된 검사다. 문장이 자연스러운지, PC·모바일을 별도 화면으로 중복 계산하지 않았는지, 품목명의 원문 보존이 적절한지는 `rawGenerated`와 `selectedSourceSnapshots`를 함께 보고 판단한다. 가격 검증이 잘못된 모델 단가를 교정할 수 있으므로 최종 합계만 확인하지 않는다.

자료 위치: [`fixtures/ai-estimate-validation/`](../fixtures/ai-estimate-validation/). 실제 고객 자료 대신 이 파일로 시작한다. [자료 README](../fixtures/ai-estimate-validation/README.md)와 [manifest.json](../fixtures/ai-estimate-validation/manifest.json)에 파일별 등록 제목·버전, 기대 추출값·오류 코드·해시가 있다.

| `prompt-injection.md` | 설계 자료 또는 작업 상세 | 자료 내부 지시가 가격 검증·근거 선택을 바꾸지 못하는지 검사 |

기준 단가는 `画面設計` 50,000엔/화면, `開発` 80,000엔/화면이며 세금 별도·소비세 10%다.

| 조건 | 설계 | 개발 | 소계 | 소비세 | 합계 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 이번 작업: 각 5화면 | 250,000 | 400,000 | 650,000 | 65,000 | **715,000엔** |
| PDF 과거 견적: 각 3화면 | 150,000 | 240,000 | 390,000 | 39,000 | **429,000엔** |
| CSV 과거 견적: 각 3화면 | 135,000 | 210,000 | 345,000 | 34,500 | **379,500엔** |
| 단가표 기반 내부 후보: 임시 각 1화면 | 50,000 | 80,000 | 130,000 | 13,000 | **143,000엔** |

PDF의 품목은 영어 `Design`·`Development`, 단위는 `screen`이며 단가는 50,000/80,000엔이다. PDF 연계 검사는 영어 단가표로 PDF 추출 실패를 가리지 않고 **실제로 추출한 PDF 두 행**을 과거 가격 근거로 사용한다. `history-ja.csv`의 과거 가격 45,000/70,000엔은 현재 단가표보다 낮도록 의도적으로 다르게 구성했다. 현재 단가표와 함께 선택했을 때는 50,000/80,000엔이 우선해야 한다.

PDF의 원본 수량 3과 이번 요구사항의 수량 5를 구분한다. 내부 검색 모드는 단가표의 임시 수량 1과 합계 143,000엔을 제시하며 5화면을 해석한 결과로 판정하지 않는다. 따라서 앱에서는 최종 작업량을 확인하고 각 5로 수정한 뒤 715,000엔을 검증한다. 실제 모델이 낸 수량·수량 설명도 사람이 원본 설계와 대조해야 한다.

## 3. API 자동 시나리오

이 suite는 DB를 만들거나 앱에 자료를 등록하지 않는다. PDF 경로는 실제 추출 → 추출값 검증·검수 데이터 변환 → 생성 컨텍스트 구성 → 실제 구조화 생성 → 서버 가격 검증을 이어서 검사한다. 승인된 자료 역할의 합성 값을 메모리에서 구성해 실제 공급자 응답과 애플리케이션의 구조화·단가 검증을 확인한다. **RLS, 실제 관리자 승인, Storage 업로드, DB 검색·벡터 품질, 문서 저장 성공은 별도 앱 E2E 대상**이다.

| Case ID | suite | 핵심 확인 |
| --- | --- | --- |
| `pdf-extraction` | smoke/full | 실제 `estimate.pdf`를 공급자가 읽고 두 품목·단가·수량·세금 기준을 구조화하는지 |
| `pdf-to-estimate` | smoke/full | 바로 앞 PDF 추출 결과를 근거로 새 작업 견적을 생성하는지. 원본 과거 수량과 새 요구 수량을 구분하는지 |
| `rate-ja` | full | 일본어 작업 요청과 승인 단가표·설계·작업 상세의 조합, 단가 및 수량 근거 |
| `rate-ko` | full | 한국어 요청·설명, 같은 가격 검증 원칙 |
| `rate-en` | full | 영어 요청·설명, 같은 가격 검증 원칙 |
| `tax-mismatch` | full | 원본 단가의 세금 포함 여부가 다른 경우 그 금액을 현재 견적에 그대로 확정하지 않는지 |
| `rate-conflict` | full | 동시에 선택한 단가표의 가격이 다르면 임의 평균·최신값으로 확정하지 않고 충돌을 알리는지 |
| `missing-price` | full | 근거 없는 품목에 모델이 가격을 써도 서버에서 0·근거 부족으로 처리하는지 |
| `prompt-injection` | full | 자료 속 지시문이 단가·출처 검증을 우회하지 못하는지 |

예상 거절·근거 부족을 올바르게 처리한 경계 검사는 성공할 수 있다. 모든 시나리오가 양의 가격을 내야 성공하는 검증이 아니다. 반대로 API 실패 후 내부 후보로 전환된 결과를 live 모델 성공으로 처리해서도 안 된다.

자동 보고서와 함께 사람이 확인할 사항은 다음과 같다.

- 한국어·일본어·영어 설명이 요청 언어로 자연스럽고, 제품명 등 원문 보존이 필요한 부분만 원문인지.
- 5화면이라는 수량이 설계·요구사항에서 나오며, 다른 자료의 과거 수량을 그대로 복제하지 않았는지.
- 제외한 작업을 포함하거나 단가표의 두 품목을 같은 작업으로 중복 산정하지 않았는지.
- 실제 근거 문서와 각 행의 단가·단위·세율이 일치하는지. 모델이 제시한 이유만으로 통과시키지 않는다.

## 4. 실제 앱 E2E 준비

API 키만으로 위 자동 검증을 실행할 수 있지만, 아래는 기존 SalesFlow 앱·인증·DB가 필요하다. 운영 자료와 분리된 검증 조직을 사용한다.

1. Supabase, 비공개 `ai-estimate-sources` 버킷, 마이그레이션 `0001`~`0038`이 준비된 앱을 실행한다. 기존 환경은 적용 상태를 확인하고, 미적용 DB에 최신 SQL 하나만 단독 적용하지 않는다.
2. 검증 조직 A에 관리자, 일반 멤버 A/B, viewer를 준비하고, 타 조직 B 사용자도 준비한다. 승인 담당은 owner/admin이다.
3. 조직 A에 합성 거래처 A/B를 등록한다. 자료 제목에는 실행 식별자(예: `AI-VALID-2026-09-24-01`)를 붙인다. 기본 프로젝트명은 `Synthetic responsive website validation`, 공개 범위는 조직 공용, 참조 유효기간은 미지정으로 시작한다. 개인·기간 검사는 별도 복제 자료로 한다.
4. `/settings/ai-estimates`에서 도우미 사용을 켠다. 먼저 외부 처리 허용을 끈 상태로 표·텍스트와 내부 검색을 검사한다.
5. 실제 모델을 앱에서 검사할 때만 해당 조직의 외부 처리 허용과 앱 서버의 API 키·모델 설정을 확인한다. CLI용 `.env.ai-validation.local`은 Next.js 앱이 자동으로 읽는 파일이 아니다. 앱 실행 환경 또는 서버용 `.env.local`에 별도로 설정하고 서버를 재시작한다.
6. 공개 웹 조사는 이 가이드의 기본 검증에서 끈다. 웹 가격을 내부 승인 단가의 대체 근거로 사용하지 않는다.

날짜 경계는 서비스의 일본 시간(`Asia/Tokyo`) 기준 당일로 정한다. 기본 자료는 참조 유효기간을 비워 재사용하고, 날짜 검사 전용 자료만 과거 종료·미래 시작·당일 시작/종료를 지정한다. 자료의 참조 유효기간은 PDF에 적힌 과거 견적 제출 유효기한과 별개다.

### 기본 등록 → 승인 → 적용 → 저장

1. `/estimates/ai-library/upload`에서 `rate-card-ja.csv`를 **단가표**, `history-ja.csv`를 **과거 견적**으로 등록한다. 프로젝트명은 같은 합성 프로젝트, 버전은 `v1`로 지정한다.
2. `design-ja.md`는 **설계 자료**, `work-scope-ja.md`는 **작업 상세**로 등록한다. 파일 대신 ‘텍스트로 등록’에도 같은 합성 본문을 붙여 넣어 볼 수 있다.
3. 등록 직후 모두 검수 대기이며, 새 견적의 승인 자료 선택 목록에는 아직 없어야 한다.
4. 검수 화면에서 가격 자료의 두 행과 `画面` 단위를 확인한다. 단가표는 50,000/80,000엔·수량 1, 과거 CSV는 45,000/70,000엔·수량 3이며 둘 다 세금 별도·10%다. 각 파일 원본과 대조한다. 설계·작업 자료는 가격 명세 없이 본문·전제·제외 범위를 확인한다.
5. 거래처 A를 연결한다. 과거 견적만 날짜가 ‘견적일’이고, 다른 자료는 ‘자료 작성일’인지 확인한다. 직접 입력한 자료에 AI 추출 신뢰도가 표시되지 않아야 한다.
6. 관리자 검수 확인 후 승인한다. 일반 멤버는 자신이 등록한 자료를 검수할 수 있어도 승인할 수 없어야 한다.
7. 자료함 또는 승인 상세의 ‘이 자료로 견적 만들기’를 누른다. 새 견적에서 자료와 거래처 A가 함께 선택되는지 확인한다. 단가표·설계·작업 상세를 함께 선택한다.
8. 제목과 작업 설명에 `画面設計と開発。各5画面。税別10%。`를 입력하고 상세 요구사항·전제·제외 작업을 확인한다. 생성 방식은 먼저 자동/내부 검색, 이후 준비된 Gemini 또는 Claude로 반복한다.
9. 두 품목과 실제 단가 근거 링크, 설계·작업 참고 자료, 수량 근거를 확인한다. 필요한 행만 적용하고 폼에서 각 수량을 5로 확정한다.
10. 소계 650,000엔·세금 65,000엔·합계 715,000엔을 확인하고 견적을 저장한다. 다시 열어 거래처·명세·세금·합계가 같은지 확인한다. 이 검증에서는 실제 고객에게 발행·이메일·우편을 보내지 않는다.

APP-20의 저장 연결은 UI 금액 확인과 별도로, 검증 DB에서 해당 견적 ID에 연결된 `ai_estimate_suggestions`를 읽어 확인한다. 관리자 SQL 도구의 조회는 저장 증거 확인용이며 사용자 RLS 검사에 대신 사용할 수 없다.

```sql
-- <검증 견적 UUID>를 저장한 합성 견적 ID로 바꾼다. 읽기 전용 검사다.
select id, estimate_id, status, provider, model,
       request_context,
       suggestion_data -> 'draft' as original_ai_draft,
       suggestion_data -> 'referenceSnapshots' as approved_source_snapshots,
       suggestion_data -> 'priceAnchorSnapshot' as price_anchor_snapshot,
       suggestion_data -> 'groundingPolicy' as grounding_policy
from public.ai_estimate_suggestions
where estimate_id = '<검증 견적 UUID>'::uuid;
```

확인할 차이는 **원래 초안 수량**과 **사용자가 수정해 저장한 최종 수량**이다. 내부 후보가 각 1이었다면 AI 원안은 1을 유지하고 최종 문서는 각 5여야 한다. 저장 후 자료 제외가 이전 문서나 당시 참고 내용까지 삭제하면 실패다. 최종 근거에는 생성 시 선택한 자료·요구사항·수량 이유와 당시 가격 정책이 남아야 한다.

## 6. 화면 크기·언어·키보드 확인

브라우저 뷰포트를 CSS 픽셀 기준 **320, 390, 768, 1440** 너비로 바꾸고 등록 → 검수 → 자료 선택 → 결과 → 견적 저장 화면을 반복한다. 기본 한국어 확인 후 일본어·영어로 주요 입력·오류·버튼을 확인한다.

| 구간 | 확인할 내용 |
| --- | --- |
| 등록 | 파일/텍스트 탭, 자료 종류·날짜·프로젝트·버전, 긴 파일명과 도움말, 제출 버튼이 잘리거나 겹치지 않음 |
| 검수 | 원본 PDF/이미지 또는 텍스트를 볼 수 있고 내용 입력까지 스크롤 가능. 날짜 입력·긴 품목·단가·세율과 승인 체크가 가려지지 않음 |
| 자료 선택 | 긴 자료명·버전·기간 줄바꿈, 선택 개수, 내부 스크롤, 잘못된 선택 해제와 거래처 변경 후 안내 |
| 결과 | 금액·세금 문구의 의미 있는 줄바꿈, 수량 근거, 단가 근거와 작업 참고의 구분, 0원·미선택 상태, 실제 생성 방식 |
| 견적 폼 | 추가/교체 후 명세 편집, 합계·저장 바가 마지막 입력이나 버튼을 덮지 않음. 화면 전체에 의도하지 않은 가로 스크롤 없음 |
| 키보드 | Tab 이동, 체크·선택·입력, 모달 닫기/Escape와 트리거로 포커스 복원. 스크롤 영역에서 키보드가 갇히지 않음 |

768px를 다른 너비의 결과로 대체하지 않는다. ‘모바일 통과’ 대신 실제 너비·언어·화면·확인 결과를 기록한다.

## 7. 실제 API 실패를 구분하는 방법

| 증상/보고서 | 확인·재실행 |
| --- | --- |
| 설정 오류·종료 2 | 환경 파일 경로, 요청한 공급자의 키, `all`의 두 키를 확인. 키 값을 로그에 출력하지 않는다 |
| 401/403 | 키 인증·프로젝트/workspace 접근과 모델 이용 권한 확인. 생성 HTTP 상태는 `diagnostics.httpStatuses`, 추출 실패는 `error.code`를 우선 확인. 앱의 외부 동의 설정과 공급자 인증은 별도 문제 |
| 모델 없음/404 | 보고서의 실제 모델 ID와 계정에서 사용할 수 있는 모델을 확인한 뒤 환경 예제의 모델 설정 변경 |
| 429·할당량/잔액 부족 | 공급자 콘솔에서 한도·사용량을 확인. 무제한 반복하지 않고 원인 해소 후 해당 `--case` 재검사 |
| timeout·네트워크·TLS | 네트워크/프록시와 공급자 상태 확인. 보고서의 추출·생성 단계 구분 후 해당 공급자 smoke 재검사 |
| JSON/스키마 불일치·출력 중단 | 잘못된 응답이 견적에 적용되지 않아야 함. 모델·case·오류 코드를 남기고 재현, 내부 fallback을 API 통과로 보지 않음 |
| 안전 정책 거절 | 합성 자료와 요청이 거절된 단계 확인. 다른 자료를 임의 전송하거나 거절을 성공으로 바꾸지 않음 |
| `context_limit` | 선택 자료가 생성 입력 한도를 초과함. 외부 요청 없이 내부 후보 안내가 나와야 하며, 자료 선택을 줄여 재검사 |
| PDF 추출 성공, 연계 생성 실패 | PDF 원본 검증과 생성 문제를 분리. `pdf-to-estimate` 재실행은 PDF 선행 추출도 다시 실행함 |
| 단가가 0·충돌/근거 부족 | 공급자 장애인지 세금/단위/가격 근거 경계인지 구분. 금액을 임의 복사해 성공으로 처리하지 않음 |
| CLI 성공, 앱 외부 생성 불가 | CLI와 앱 서버가 읽는 환경 파일, 서버 재시작, 현재 조직 동의·역할·일일 한도를 각각 확인 |
| 외부 키 표시가 ‘설정됨’ | 설정 감지일 뿐 실제 인증·모델 접근·과금·응답 품질 성공 증거가 아님. live 보고서 필요 |

실제 장애를 재현하기 위해 운영 키를 폐기하거나 조직 과금 한도를 소진할 필요는 없다. 모의 실패 회귀와 실제 합성 자료 live 검사를 구분하고, 실제 발생한 실패는 안전하게 마스킹된 보고서로 남긴다.

## 8. 검증 기록과 정리

검증 기록에는 커밋/실행 시각, report 경로, 공급자·실제 모델, offline/live 여부, 성공·실패·미실행 case, 수동 확인 언어·화면 너비, 앱 조직·합성 견적 ID를 남긴다. API 키는 기록하지 않는다. 모델이 원래 반환한 `rawGenerated`와 서버에서 근거로 확정한 `result.draft`를 `selectedSourceSnapshots`에 대조한다. 부분 성공은 성공한 공급자와 case까지만 적는다.

API 자동 suite는 DB를 사용하지 않는다. 앱에 등록한 합성 자료·거래처·견적은 별도로 관리한다. 테스트 후 합성 자료를 추천 대상에서 제외하고, 삭제가 필요하면 해당 실행에서 만든 ID만 기존 앱/검증 환경 절차로 정리한다. 이미 존재하던 자료를 일괄 삭제하거나 운영 DB를 초기화하지 않는다. 보고서에 남길 실패 증거와 저장 스냅샷을 확인한 뒤 정리한다.

관련 설명: [자료 저장·검색·산출 흐름](AI_ESTIMATE_DATA_FLOW_2026-09-24.md), [RAG 운영 안내](AI_ESTIMATE_RAG.md).
